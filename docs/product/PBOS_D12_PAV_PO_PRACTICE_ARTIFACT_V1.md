# PBOS D12 · PAV Receita Federal · PO Practice Artifact v1

**Status:** Draft for user validation  
**Gate:** DG-03  
**Purpose:** Transform the real PAV Receita Federal experience into a Product Owner practice artifact without rewriting historical facts.

> **Important distinction:** this is a reconstructed PO practice artifact created by PBOS. It is not an original formal Product Owner document from the PAV project.

---

## 1. Historical evidence used

The documented PAV experience supports the following facts:

- The initiative originated from a Prefeitura demand to make Receita Federal services more accessible to citizens in Maricá.
- The user participated from Discovery through implementation and delivery follow-up.
- Discovery included conversations with citizens, journey mapping, data analysis, meetings with other areas, direct interaction with Receita Federal and requirements definition.
- Receita already had a PAV model and service framework used in other locations.
- The user participated in visiting one existing PAV point to observe equipment, layout, service types, execution, support, system access and training.
- The solution was implemented in three neighborhoods/units in Maricá.
- The user participated in validation with users and in post-launch support.
- Public institutional material confirms the PAV model and the existence of PAV units in Maricá.
- A Receita representative/auditor gave positive qualitative feedback, stating that the work exceeded expectations and was ahead of comparable cities, according to the documented experience.
- No quantitative attendance, satisfaction or citizen travel-reduction metric is being invented in this artifact.

---

## 2. Service problem

### Problem statement

Citizens in Maricá could face unnecessary travel to access Receita Federal services that could be facilitated locally through a partner-operated PAV model.

The opportunity was to understand which services and operating conditions could be implemented locally, adapt an existing Receita model to Maricá and make the service available closer to citizens.

### Service opportunity

Use an existing institutional service model, understand local user needs and operational constraints, define concrete requirements and implement a validated local service point rather than creating an entirely new service model from scratch.

---

## 3. Users and stakeholders

### Primary user

**Citizen/taxpayer in Maricá**, who needs access to eligible Receita Federal services without unnecessary displacement.

### Key stakeholders

- Prefeitura de Maricá
- Receita Federal
- project/team areas involved in implementation
- local service points/units
- citizens using the service

The user participated in stakeholder alignment and requirements definition, but did not independently own the entire product/service strategy.

---

## 4. Reconstructed user need

> As a citizen/taxpayer in Maricá, I need access to eligible Receita Federal services locally, with clear guidance and an operational process that allows my request to be handled or forwarded correctly.

**Classification:** reconstructed user need for PO practice.  
**Historical status:** the experience supports citizen-focused discovery and journey mapping, but this exact wording was not an original PAV User Story.

---

## 5. Reconstructed product/service objective

### Objective

Implement a local PAV service that enables eligible Receita Federal requests to be handled, guided or digitally forwarded according to the institutional model, with the physical, technical and operational conditions required for service delivery.

This objective is a PO-format reconstruction based on the historical implementation work.

## 6. Discovery and journey logic

The documented Discovery can be represented as:

**Citizen need**  
→ understand local problem  
→ talk to citizens  
→ map journey  
→ analyze available data  
→ understand eligible services  
→ align with Receita Federal  
→ define requirements  
→ benchmark one existing PAV  
→ adapt implementation to Maricá  
→ implement 3 units  
→ validate with users  
→ support operation.

The key competency is **Service Discovery**, not simply project execution.

---

## 7. Requirements and decomposition

The implementation required concrete operational requirements, including aspects such as:

- physical layout/location;
- desktop/computing equipment;
- printer;
- scanner;
- internet connectivity;
- access to Receita systems;
- service execution conditions;
- support/training conditions;
- operational readiness before service start.

The user participated in defining these requirements and in checking implementation readiness.

**Important:** the user did not independently design the entire PAV solution. Receita's existing model was the reference, and the work involved understanding, benchmarking and adapting it to Maricá.

## 9. Reconstructed acceptance criteria

For the service to be considered ready for operation:

- physical location and layout are prepared;
- required equipment is available;
- connectivity is available;
- required system access is available;
- operational conditions defined with Receita are satisfied;
- responsible staff have the required orientation/training;
- service flow is understood by the participating team;
- readiness conditions are checked before service begins;
- user validation can identify operational or journey friction.

These are **practice acceptance criteria**, not claims that the PAV project recorded them formally in this exact format.

---

## 10. Benchmarking and adaptation

A relevant Product/Service practice demonstrated by this experience is **benchmarking an existing solution before implementation**.

The user visited one existing PAV point to understand how the model worked in practice, including physical structure, equipment, service execution, support and training.

The model was then implemented across three Maricá units.

**Do not claim:** that the user visited three benchmark units or created the PAV model from scratch.
